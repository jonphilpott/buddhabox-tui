BuddhaBox TUI guide

A virtual BuddhaBox in the terminal, for macOS and Linux (x86 and Raspberry Pi): the framework's DSP modules, the computer's own sound card and MIDI, and a panel of knobs, switches and a display played from the keyboard.

Overview

The BuddhaBox framework runs on an STM32 Black Pill with an I2S DAC, pots and an OLED. This project runs the same DSP modules on a desktop or a Raspberry Pi, and replaces the hardware with a panel drawn in the terminal. It began as a copy of the framework's DSP library and is free to diverge from it.

Design principles

  • A sketch, not an app. A program defines setup(), loop() and audioCallback(), as on the board. The library supplies main().
  • Native only. CoreAudio and CoreMIDI on macOS, ALSA on Linux, raw terminal codes for the panel. No JACK, no ncurses, no PortAudio: nothing to install but a compiler (and the ALSA headers on Linux).
  • The same DSP. src/buddhabox/ is the framework's module library, header-only, sample by sample, floats normalised to ±1. Code moves between the two projects with little change.
  • Memory is plentiful. Buffers are still fixed arrays sized by template parameters, but in seconds rather than kilobytes: DelayLine<441000> is a 10 s echo.

Quick start

1. Install a compiler

macOS

xcode-select --install     # clang, make and git

Linux and Raspberry Pi OS

sudo apt install build-essential libasound2-dev   # Debian, Ubuntu, Pi OS
# sudo dnf install gcc-c++ make alsa-lib-devel    # Fedora

2. Build and run

make              # every example, into build/
make acid         # just one
./build/acid      # Ctrl-C to quit

The panel needs a terminal of at least 80 × 26 characters (80 × 10 for programs that don't use the display), plus one row for programs that use the LEDs.

3. Start your own

python3 tools/new_project.py ../my_synth            # from examples/sine
python3 tools/new_project.py ../bells --example singing_bowls
cd ../my_synth && make && ./my_synth

The new folder holds main.cpp, a Makefile that builds against this checkout, and a .gitignore. Or add a folder to examples/: make finds every examples/<name>/main.cpp by itself.

4. The smallest program

This is examples/sine/main.cpp, a tone played from a knob or a MIDI keyboard:

/**
 * @file main.cpp
 * @brief The smallest buddhabox-tui program: a sine tone you can play
 *        from a knob or a MIDI keyboard.
 *
 * Every buddhabox-tui program has the same parts:
 * 1. DSP objects as globals (from buddhabox-framework).
 * 2. audioCallback(): fills each block of output on the audio thread.
 * 3. setup(): labels the panel, configures the objects, starts audio.
 * 4. loop(): reads the panel and MIDI on the main thread and hands the
 *    results to the audio through plain globals.
 *
 * Panel:
 *   knob 0 (a/z)  Pitch, 55 Hz to 880 Hz
 *   knob 1 (s/x)  Level
 *   switch 0 (1)  Mute
 *   MIDI          a note on sets the pitch
 */

#include "bbtui/tui.h"
#include "buddhabox/core/dsp_common.h"
#include "buddhabox/core/midi_utils.h"
#include "buddhabox/osc/sine.h"

using namespace bb;

// 1. DSP objects, and the settings loop() hands to the audio thread.
SineOscillator osc;
float hz = 220.0f, level = 0.3f;
bool mute = false;

// 2. The audio: one sine, the same on both channels.
void audioCallback(const float *in, float *out, int frames) {
  float gain = mute ? 0.0f : level;
  for (int i = 0; i < frames; i++)
    out[2 * i] = out[2 * i + 1] = gain * osc.next(hz / SAMPLE_RATE);
}

// 3. Set-up.
void setup() {
  tui::setTitle("SINE");
  tui::setKnob(0, "Pitch", 0.5f);
  tui::setKnob(1, "Level", 0.3f);
  tui::setSwitch(0, "Mute");
  Midi::begin();
  AudioEngine::begin();
}

// 4. Controls. The pitch knob covers four octaves; fastExp2() turns its
//    0-1 into a ratio, so each tenth of the knob is the same interval.
void loop() {
  hz = 55.0f * fastExp2(4.0f * tui::knob(0));
  level = tui::knob(1);
  mute = tui::switchOn(0);

  // A MIDI note sets the pitch knob to match, so the panel shows it.
  Midi::Message m;
  while (Midi::read(m))
    if (m.isNoteOn())
      tui::setKnob(0, "Pitch", fastLog2(midiToFreq(m.data1) / 55.0f) / 4.0f);
}

LEDs

Sixteen indicators for the program to use as it likes. Each takes a colour from 0 to 1: 0 is off, and anything above picks a hue around the colour wheel. They don't belong to a page: all 16 are always on screen.

ValueConstantColour
0tui::LED_OFFOff
1/6tui::LED_YELLOWYellow
1/3tui::LED_GREENGreen
1/2tui::LED_CYANCyan
2/3tui::LED_BLUEBlue
5/6tui::LED_MAGENTAMagenta
1tui::LED_REDRed

Values in between blend (0.08 is orange), so a level can drive a colour directly. tui::setLedFlash(i, true) makes an LED blink twice a second, in step with every other flashing LED.

tui::setLed(0, tui::LED_GREEN);  // running
tui::setLed(1, level);           // a level as a colour
tui::setLed(3, tui::LED_RED);
tui::setLedFlash(3, true);       // a warning

examples/acid shows its 16-step sequence on them: red an accent, green a plain note, off a rest, flashing a slide, cyan the step playing.

Pages

There are four pages of 10 knobs and 20 switches. In code, knobs are numbered 0–39 and switches 0–79, page by page: knob 12 is the third knob on page 2 (keys d/c), and switch 25 is the sixth switch on page 2 (key 6). The title bar shows the pages as [1234]: the page on screen bold, empty pages dim. Changing page lets go of any held knob or momentary switch, so a key coming up on the new page can't strand one on the old.

Key releases

An ordinary terminal reports a key going down, and repeats it while held, but never reports it coming up. The panel works within that:

  • A knob key steps the knob by 0.01 (0.001 with Shift) on each press and on each repeat.
  • A momentary switch lights for 150 ms per press.
  • A toggle ignores presses that come within 120 ms of the last one: those are the keyboard's repeats, not new presses.

kitty, WezTerm, Ghostty, foot and recent iTerm2 speak the kitty keyboard protocol, which reports releases. The panel asks at start-up and, when it is there, holds work as they should: a held knob key sweeps smoothly after 0.3 s (the full range in 2.5 s, or 20 s with Shift), and a momentary switch stays lit until its key comes up.

How a program runs

Two threads, as on the board, where loop() and the DMA interrupt share the processor:

keys, MIDImain thread → loop()~1000 times a second → globalsfloats, bools → audioCallback()audio thread, 256 frames → sound card44.1 kHz stereo

loop() reads the panel and writes settings into globals; the audio thread reads them. The panel redraws 30 times a second between calls to loop().

  • setup() runs once: label the panel, configure modules, call AudioEngine::begin().
  • loop() runs about 1000 times a second on the main thread. Read knobs, switches, the menu and MIDI; draw on the display. Never block in it: the keys and the panel are handled between calls.
  • audioCallback(in, out, frames) runs on the audio thread. in and out are interleaved stereo floats, −1 to 1; frames is 256. No printing, waiting or allocation in here.
Sharing values between the threads. Do as the board does: loop() writes a float or bool and the callback reads it. Strictly, C++ calls this a data race; on x86 and ARM an aligned 32-bit store can't be half-written, so the callback sees the old value or the new one. For anything bigger, such as a sequence being rewritten, at worst one step plays half old, half new.

Audio and MIDI

Output and input

AudioEngine::begin() opens the default output at 44.1 kHz; begin(true) opens the default input too. The operating system converts to the device's own rate. Input reaches the callback through a lock-free queue, a few blocks behind, so playing through dry is a little late (fine for echoes; see examples/fx).

input deviceits own thread → queuelock-free, 8 blocks → audioCallback()in[], out[] → output device

If the input's clock runs faster than the output's, the queue drops its oldest samples beyond 4 blocks, so the delay can't grow.

AudioEngine::cpuLoad() and cpuPeak() report the share of each block's time spent in the callback; the title bar shows both. A peak at or above 100% means a block was late and the sound glitched.

MIDI

Midi::begin() connects every MIDI input present at start-up. In loop(), take messages until there are none:

Midi::Message m;
while (Midi::read(m)) {
  if (m.isNoteOn()) playNote(m.data1, m.data2 / 127.0f);
  else if (m.isCC() && m.data1 == 74) cutoff = m.data2 / 127.0f;
}

Notes, control changes, program changes, pitch bend, clock, start, stop and continue all come through. The title bar's MIDI light flashes for each message except clock.

Display and menu

tui::display() returns the virtual OLED: the board's Oled drawing calls (pixel, line, rect, text, number) on a 128 × 64 buffer, without begin() or display(). Draw in loop(); the panel shows whatever is in the buffer on its next frame. Nothing appears until something is drawn.

Menu is the board's menu with one change: the board has a single encoder, so it needs an edit mode (press to change a value, press again to move on). With four arrow keys there is none: up and down move, left and right change the highlighted value, and space runs action items.

Menu::Event e =
    menu.update(tui::menuMove(), tui::menuAdjust(), tui::menuPressed());
if (e == Menu::CHANGED)
  applyMenu();
else if (e == Menu::ACTION && menu.selected() == RANDOMIZE)
  randomize();
menu.draw(tui::display(), 16, 6); // six rows below a 16-pixel header

A knob can stand for a menu item, as on the board, and here the menu can move the knob back, since a virtual pot can be turned from code: call tui::setKnob() when the menu changes it. examples/acid and examples/noisebox do both.

Where the DSP comes from

src/buddhabox/ was copied from buddhabox-framework at commit 7c5c012, without its board-only io/ and engine/. Change it here freely. Differences so far:

  • DelayLine takes a 32-bit size (the board's is 16-bit, 1.49 s at most). Positions are floats, which hold whole numbers exactly up to 224 samples, about 6 minutes; beyond that, delay times round.

The lookup tables (lut*.h) were generated by the framework's tools/gen_tables.cpp, which was not copied.

Platform notes

  • macOS: audio through AudioQueue (three blocks queued, about 17 ms), MIDI through CoreMIDI. A program that opens the input asks once for microphone permission, on behalf of your terminal app; to change your answer, see System Settings, Privacy & Security, Microphone.
  • Linux: audio through ALSA's default device, which goes through PipeWire or PulseAudio where they run. Choose another with BB_AUDIO_OUT and BB_AUDIO_IN, e.g. BB_AUDIO_OUT=plughw:1 ./build/acid; aplay -l and arecord -l list the cards. MIDI through the ALSA sequencer; devices plugged in later can be connected with aconnect <device> buddhabox-tui.
  • Real-time priority (Linux): the audio threads ask for it and carry on without. To grant it, add @audio - rtprio 95 to /etc/security/limits.conf and join the audio group.
  • Raspberry Pi: the panel works over SSH, so a Pi with no screen is an instrument you play from a laptop.
  • If a program crashes, the terminal may be left in raw mode: type reset and press Enter.
